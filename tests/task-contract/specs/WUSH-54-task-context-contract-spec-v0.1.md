## 1. 合同结构与来源（FR-01 / FD-01）

以下为**语义字段表，不是 canonical JSON Schema 或已存在的接口**。JARVIS 在核验后维护唯一实现契约；不得把本表另生成一套平行状态。任务是 Issue；单次执行是运行（API 的 `task_id`）。

### 1.1 公共结构

- `Actor = {type: member|agent, id: UUID}`：须同工作区、有效；显示名不是身份。首版下一责任人与接回人均用具体 Actor，不用未解析的 squad 或自由文本。
- `Source = {kind: issue|comment|document|artifact, locator, version, digest, supplied_by}`：至少一个可定位的固定来源；内部资源校验真实 ID、归属和可读性。可编辑来源记录其 revision 与内容摘要；仓库文档记录仓库、路径、commit SHA。摘要不代替读取权限。
- `Resource = {kind: repository|issue|document|artifact, locator, match: exact|directory}`：仓库资源用仓库身份 + 规范化相对路径；`directory` 仅允许事先批准的目录前缀，不支持任意 glob、正则或路径逃逸。其他资源仅 `exact`。
- 所有 ID 在单份快照中唯一；所有引用必须解析。文本去首尾空白后非空。以下字段全部必须出现；仅标明允许的数组可为 `[]`，不能用 `null`、空白、“同上”或占位文字替代。

### 1.2 必填字段

| 字段 | 内容与最小校验 | 来源 / 谁负责 |
| --- | --- | --- |
| `schema_version`、`contract_id`、`issue_id`、`workspace_id`、`version` | 首版格式版本为 1；合同 ID 稳定；每任务最多一个当前版本；版本正整数 | 平台生成/绑定，调用者不得改归属或回拨版本 |
| `goal`、`goal_sources` | 一个当前目标，非空文本及至少一个固定来源 | 发起方提炼已授权需求；历史摘要不能自证授权 |
| `allowed_actions` | 至少一项 `{id, operation, resources, acceptance_ids}`；operation 首版为 `read|edit|test|deliver`；每项资源及验收引用非空 | 发起方按本阶段获准动作列出；不是赋予工具或账号权限 |
| `prohibitions` | `{text, denied_actions}`；text 非空；denied_actions 是同结构的明确禁用操作/资源，允许 `[]` | 授权边界；未能结构化判断的自然语言约束仍需责任人复核，不得伪报已机器理解 |
| `acceptance` | 至少一项 `{id, assertion, evidence_required, source_refs}`；断言有观察对象、期望结果及证据类型 | 已批准需求；不以“效果好”“完成即可”为验收 |
| `effective_inputs` | 至少一项 `{id, source, purpose, required}`；主需求来源必须列入 | 发起方指定本阶段有效材料；日志、原始对话不是默认有效指令 |
| `confirmed_facts`、`assumptions` | 分开的数组，可 `[]`；事实含 assertion、source_refs；假设含 assertion、validation、owner、blocks_start | 事实须可追溯；假设不能自动升格为事实。`blocks_start=true` 的未验证假设阻止开工 |
| `versions` | 任务内容快照、代码基线、文档基线，规则见下 | 平台取任务快照；发起方指定源码/文档，运行时提供本地观测 |
| `deliverables` | 至少一项 `{id, description, acceptance_ids, evidence_refs}`；evidence_refs 初始可 `[]`，表示尚未交付 | 发起方定义预期产物；后续实际 SHA/附件/测试证据是独立来源，不把预期当已实现 |
| `open_questions` | `{id, question, owner, blocks_start}` 数组，可 `[]` | 发起方；阻断问题未关闭前不能接手；关闭必须通过新版本并附来源 |
| `stop_conditions` | 至少包括缺有效输入、版本不符、结构化动作越界、授权不足、阻断问题；各项有 code、condition、return_to | 发起方引用本表标准停止项，可补充本阶段已批准条件 |
| `next_owner`、`return_to` | 两个有效 Actor；前者执行本阶段，后者收回澄清；不能省略、不能仅写“找负责人” | 发起方；接回人不因拒绝而自动派工或被改为任务 assignee |
| `decision_sources` | 至少一项已授权范围的固定依据；记录来源、作出决定者和时间，不伪造人类签署 | 本任务说明可作为本批委派依据；超出既有授权的变化必须先有人类确认 |
| `change` | `{reason, source_refs}`；初版写建立原因，后续写修改原因；均非空 | 发起方提供；服务端补 actor、时间、from/to、changed_fields |

`versions` 必须区分三种版本：

1. `issue_basis = {revision, title_digest, description_digest}`：发布时平台读取；revision 是并发快照/证据，不是合同版本。评论等也会推进任务 revision，**不能要求每次开工整个 revision 相等**。开工比对标题/描述摘要；变化即 `source_changed`，须发起方确认重建版本，不自动采用新目标。
2. `code_basis[] = {repository, commit_sha, branch, dirty_snapshot}`：SHA 必须是完整固定 commit；branch 只作说明。干净基线的 dirty_snapshot 为 `null`；有未提交修改时必须是可恢复补丁/文件快照的附件引用及摘要，不能填“当前工作区”。没有代码活动时使用 `code_basis: []` 加非空 `code_not_applicable_reason`，不得虚填 SHA。
3. `document_basis[] = {source, applicability}`：至少包含主需求来源；固定版本与摘要，禁止用浮动 URL 当固定版本。其他失效/未获权限材料不能当有效输入。

## 2. 当前版本、历史与变更（FR-02 / FD-02）

1. 只有完整、来源可读且已通过发布校验的快照能成为当前合同。未提交表单仅是草稿，保存草稿不派工、不等于合同有效。
2. 首次发布版本 1；每次成功变更版本 +1，旧快照只读。服务端原子保存新快照、当前指针和变更记录；任何一步失败均不切换当前版本。不得覆盖/删除历史，也不提供“回拨版本”接口；恢复旧内容也要生成新版本并记录原因。
3. 每次发布都要求 `expected_version`（首次为 0）及 `expected_issue_revision`，两者均严格比较。两名编辑者基于同一版本提交，只允许一个成功；另一方得到冲突，保留其表单，重读比较后再提交。普通评论也可能令**发布请求** revision 冲突，此时重读任务后可按原内容重新提交；它不令已发布合同过期，也不要求凭空生成新版本。开工的 stale 判断仍只按 §1 的内容/引用指纹，不比较聚合 revision。无变化提交不增版本、不追加伪变更。
4. 变更记录最少有 `from_version`、`to_version`、`changed_fields`、reason、source_refs、actor、服务端 RFC3339 时间。目标、允许/禁止范围、验收以及任何其他合同字段变化都可追溯；来源时间与服务端记录时间分开。
5. 新版本使旧版本未接手交接失效，不把旧确认、旧准入结果、旧输入摘要迁移为新版本已确认。已经完成的交付及其证据保留版本绑定，不回写为新版本通过。
6. **最小并发策略候选：** 该任务存在 `dispatched|running|waiting_local_directory` 运行时拒绝发布新版本（`contract_run_active`）。调用现有停止入口并确认终态后才能发布；不能以“已请求取消”当“已停止”。仅有 queued 时允许发布，**发布事务同时终结该任务所有旧版绑定的 queued 项**为现有 `cancelled`，原因 `contract_stale`，并使对应 pending 交接 stale；不等下一次 claim 才清理，不自动重试。发布与 claim/start 必须互斥裁决：发布先成功则旧版不能被 claim/start；claim 先成功成为 dispatched 则发布失败。此策略避免本批扩成运行中热换合同/通用撤权系统。
7. 直接改任务正文、发评论或自由摘要都不是合同发布。正文变了触发下一次校验失败；普通评论不自动成为决定。运行中若提出目标变更，先停止受影响工作，不把新评论静默拼为当前指令。

## 3. 开工门、状态与接回（FR-03 / FD-03）

### 3.1 两次裁决，不靠一句提示词

**发起交接时：** 服务端校验当前版本、结构、引用、阻断项、目标责任人和现有调用权限，保存带版本的交接记录；仅通过后才允许走现有 assignment/dispatch 链路。运行可排队，但 queued 不等于已接手。

**实际开工时：** claim/start 所有现有入口使用同一准入语义，包括单/批 claim、手动 rerun、自动 retry、唤醒与会话恢复；必须重新验证：

- 当前合同存在、格式受支持，交接绑定的版本仍是当前版本；来源、任务内容指纹和接收方没有漂移。
- 所有必需输入可用、摘要/版本一致；没有阻断问题或阻断假设。
- `planned_action_ids` 非空且属于 allowed_actions；声明的操作/资源落在允许集合且不命中 denied_actions；禁止项优先。未知操作、未知资源、路径逃逸或未声明动作一律不准入。
- 平台确认当前身份、工作区、目标智能体 Access、运行时归属；合同不能代替已有权限。目标成员只能以本人接手；智能体接手绑定平台认证的目标智能体和运行时，不信任请求体自称身份。
- 代码输入由获认证运行时提交实际 SHA/未提交快照观测并与合同匹配；平台不能谎称能直接读取任意本地目录。采集此观测只允许读取元数据，不执行业务命令；缺观测时失败关闭。

服务端在持久化接手回执与将现有运行置为可启动之间进行同一并发裁决，回执绑定 `handoff_id + version + target + task_id/claim_generation + input_digest + planned_actions`。仅“预检查通过”的布尔值不可用于后续开工。未收到有效准入前，不启动模型/业务命令、不改源码、不触发下游运行。

### 3.2 状态不是另一套看板生命周期

| 交接状态 | 含义 | 下一动作 / 责任 |
| --- | --- | --- |
| `pending` | 当前版本交接已创建，等待实际准入；可附现有 queued 运行 | next_owner，尚未宣称执行开始 |
| `accepted` | 成员本人或智能体实际 start 的准入原子通过，有版本化回执 | next_owner 执行；不等于交付/测试/验收通过 |
| `needs_clarification` | 缺字段、输入、来源或存在阻断问题 | return_to 补来源/新版本，再显式交接 |
| `conflict` | 相互引用不一致、接收方或声明与合同冲突 | return_to 澄清，不让接收方猜 |
| `stale` | 旧合同、任务内容或固定输入版本变化 | return_to 更新版本；新接收方重新确认 |
| `out_of_scope` | 结构化计划超出允许动作/资源或命中禁止 | return_to 核对授权；不能点“忽略继续” |
| `unavailable` | 目标/运行能力不可用、未支持协议或临时服务故障 | return_to 排障；无准入则不执行 |

拒绝结果须持久可查，包括原因码、字段路径、所检查版本、当前版本、检查时间、return_to、相关交接/运行 ID。未经授权的请求不创建跨租户记录、不泄露当前版本、接回人或输入。`GET`/预检查不产生运行或隐式改 assignee。

不新增 Issue status 或 Run status：上表是附属交接事实。同步拒绝不得产生运行；已排队任务在开工门失败时保留该运行及来源，使用现有 `cancelled` 终态，记录“准入被拒、从未开工”，不进入自动失败重试。Issue 的 `blocked` 是否写入沿既有工作流规则，不能用它替代上述具体事实或误称运行已停止；禁止由读操作改状态。接回引用不自动发通知、评论、派工。

### 3.3 能力边界必须诚实

机器校验覆盖**结构化声明、固定版本、平台准入、平台交接副作用**；不承诺理解任意自然语言矛盾，也不承诺阻止已启动进程的一切本地 shell、Git 或外网副作用。智能体执行中发现未声明动作、语义冲突或输入不足，必须停止并回报，不扩大计划。若业务要求“任意越界工具调用都由平台拦截”，必须另审工具级隔离，不可把本批提示词纪律包装成该能力。测试应明确证明机器拒绝，而非只断言提示词包含“停止”。

## 4. 接口语义、错误与权限（FR-04 / FD-04）

以下为 App API 的**候选路由与语义**，不是已上线接口；不扩展 Public API v1、Plugin scopes 或 CLI 公共命令。JARVIS 可在保持语义及唯一契约的前提下向 Asurada 提交路由调整。

| 候选操作 | 请求与响应语义 | 副作用边界 |
| --- | --- | --- |
| `GET /api/issues/{id}/task-contract` | 返回当前完整必要快照和版本；不存在返回 404 `contract_missing` | 只读，不加载历史全文 |
| `PUT /api/issues/{id}/task-contract` | 完整快照、expected_version、expected_issue_revision、change；成功初建 201 / 更新 200，返回服务端版本与变更记录 | 不派工、不改任务状态；按 §2 原子发布 |
| `GET .../task-contract/versions?cursor=&limit=` | 只列版本、变化字段、原因、来源、actor、时间；默认 20，最大 100，返回 next_cursor；按版本倒序稳定游标 | 不默认携带每个版本全文 |
| `GET .../task-contract/versions/{version}` | 返回指定只读快照；历史不得伪装当前 | 同当前合同的资源访问门 |
| `POST .../task-contract/handoffs` | current_version、planned_action_ids、请求资源、目标、幂等键；目标必须等于 next_owner；返回 handoff 和现有 dispatch outcome | 成功后调用现有派工链路一次；成员目标不触发智能体运行；排队/合并/拒绝分别报告 |
| `POST .../task-contract/handoffs/{handoff_id}/accept` | 成员目标由本人确认；智能体由现有 claim/start 内部流程裁决，不允许 Web 冒签为智能体；返回绑定回执或拒绝结果 | 此独立成员操作不派工；智能体开工复用同一准入服务 |

交接创建是显式执行动作，服务端须持久去重：键限定工作区、调用者、操作、任务，载荷摘要包含合同版本。每次先校验当前访问权限，再查询去重记录；同键异载荷返回 409 `idempotency_conflict`。同键同载荷且原版本仍有效时返回原交接/运行 ID，不再派工；原版本已被替代时返回 409 `contract_stale`、原交接/运行 ID 及当前版本，不把原 accepted 作为当前成功结果。历史原回执保持只读。新版本交接使用新键。超时后以同键重试查原结果，不换键盲目再发。已有队列合并仅限同任务、同接收方、**同合同版本**；不同版本不能合并后沿旧上下文继续。重复回执不会再派工。

成员目标的 accept 端点只接受 next_owner 本人的认证；对智能体目标一律返回 403 `agent_accept_via_runtime_only`，包括用户在 Web 上试图代签的请求。智能体仅在现有认证运行时 start 流程生成 accepted。两类回执都含 handoff_id、version、target、input_digest、planned_actions、accepted_at；成员回执的 task_id/claim_generation 明确为 null，智能体回执必须有真实运行/claim 绑定。

错误沿用 App API `error` 英文兼容字段，增加稳定 `code`；交接派工同时沿用 `dispatch.status/reason_code`，不改现有字段含义。通过现有入口触发失败时，应能从 reason_code 定位合同准入记录。面向已授权读者的合同错误另含 `handoff_state`、`field_errors[]`、expected/current_version、return_to、request_id；不以 HTTP 200 表示开工成功但偷偷跳过校验。

| HTTP / code | 状态 / 处理 |
| --- | --- |
| 400 `invalid_request` | 格式、类型、非法 UUID/路径、缺并发前提；不提交 |
| 401 / 403 | 未登录 / 现有权限拒绝；不泄露私有目标、合同内容或资源细节 |
| 404 `contract_missing` / `not_found` | 有权访问该任务但无合同时明确缺合同；无权/不存在的资源沿现有非枚举规则 |
| 409 `revision_conflict` / `contract_version_conflict` | 发布并发失败，保留表单重读；不覆盖新值 |
| 409 `contract_run_active` | 拒绝合同热变更，保留当前版本 |
| 409 `contract_stale` / `source_changed` / `input_version_mismatch` | `stale`；回 return_to，禁止复用旧准入 |
| 409 `contract_conflict` / `receiver_mismatch` | `conflict`；列出已授权可见的冲突字段 |
| 409 `contract_out_of_scope` | `out_of_scope`；不启动，不自动申请扩权 |
| 422 `contract_incomplete` / `input_unavailable` / `blocking_question` | `needs_clarification`；字段级原因；不能当空材料通过 |
| 409 `contract_protocol_unsupported` | `unavailable`；升级受支持预览运行时，不能回退无校验 |
| 409 `idempotency_conflict` | 相同键的不同载荷；无额外副作用 |
| 503 `validation_unavailable` | `unavailable`；查询/存储/校验故障不当放行；可重试同键，不虚报已接手 |

权限候选保持最小复用：读合同/历史/准入结果沿现有任务工作区访问权限，并逐个保护引用资源；发布和交接须已有任务编辑权，涉及智能体还须现有 Access/调用权与归属校验。owner/admin 不因此绕过私有智能体 Access。角色名称/合同 next_owner 不授予仓库、部署、费用或外部系统权限。第一版不增加“合同管理员”、不新增成员/运行时权限。扩大已确认目标、权限、产品边界或验收要求，必须先补人类批准依据；Asurada 协调核验不等于自动取得扩权授权。

## 5. 最小上下文与兼容（FR-05 / FD-05）

1. 开工输入先给完整当前合同及准入绑定、当前任务必要身份/内容和必需输入的短说明/固定引用。不得裁掉目标、禁止项、验收、阻断问题、停止条件或责任人；若仍过大，返回信息不足/不可加载并停止，不静默截断。
2. 历史决定、原始对话、执行日志和 source_context 仅为证据，按引用单条/分页加载；默认不传完整历史/日志。即使恢复旧会话，也必须提供当前版本，不把旧会话的目标、自由摘要或引用文档中的指令升级为当前合同。
3. 追加普通评论、反应或附件不因聚合 revision 变化而自动使合同过期；若它们被引用为有效输入，则按该具体引用的 revision/digest 校验。被编辑的已引用决定即 stale，不能静默换内容。
4. 首次发布合同的同一事务写入该任务**不可回退的 `contract_required=true` 采用事实**；默认 false，失败发布不采用。该标记是准入要求，不是第二套任务状态，随任务只读元数据返回；只有首次发布能置 true，普通任务更新不能修改它。采用后即使当前合同丢失/损坏仍拒绝开工（`contract_missing`/`contract_incomplete`），不能通过删合同、旧客户端、不携带字段、legacy claim、重试/唤醒/会话恢复逃过门禁。未采用任务保持既有行为，不全局迁移或强制填合同。删除/取消采用不是本批功能。
5. 不改既有任务/运行枚举与字段含义；新增响应字段须 schema 解析和未知枚举安全回退。客户端未知准入状态显示“无法确认，暂不可接手”，不能 parse fallback 成 ready/accepted。旧后端缺端点时明确不支持，不回退仅提示词执行；旧运行时不能执行受保护任务，非试点仍兼容。
6. 本批只验收 Web；复用 core/views 的数据与共享视图边界，不另做独立工作流平台。桌面旧版保持 API 可读兼容，但不宣称新交接功能已在桌面/移动端完成。

## 6. 最小 Web 使用流程（FR-06 / FD-06）

1. **先验证入口：** 隔离预览可登录、进入测试工作区、创建/打开普通任务、读取评论；请求携带正确工作区，刷新后身份/任务仍正确。失败先停，不叠加合同试用。
2. **建立合同：** 任务详情内填写 §1 字段；缺项在相应字段提示，不发布、不派工；有效发布后展示当前版本、目标、允许/禁止、验收、停止条件、接收人与接回人。无需全文阅读历史才能理解本阶段任务。
3. **交接：** 确认目标与验收，选择既有有效目标和已批准动作，显式提交交接；界面区分 pending/queued 与 accepted。成员本人确认或智能体实际开工门通过后，展示谁在何时接手哪个版本及关联运行。单击、双击或网络重试不重复派工。
4. **异常停止：** 缺资料、旧页面版本、越界动作、权限失效或服务不可用时展示具体原因、当前版本、接回责任人及“查看当前合同/返回修改”等可操作入口；不提供“忽略并执行”。拒绝后刷新仍能查到交接结果，不靠弹窗作为唯一证据。
5. **变更追溯：** 修改目标/边界/验收须填原因与来源；成功后版本增加，可展开具体旧版及变更记录。旧标签页交接必须失败并重读；不会覆盖新版本、伪造接手或丢失草稿。
6. **运行中修改：** 明确提示存在活跃运行，保留表单；停止请求与已停止分开。确认终态后重新发布并交接，不热换当前合同。

预览验收前提：TARS/Data 后续交接固定源码 SHA、制品摘要（若构建）、非生产数据库标识、专用端口、独立配置和日志/停止说明；使用本 checkout 公共环境脚本，禁止拷贝生产配置/工作区数据、连接生产数据库、切换 `api.multica.ai` daemon 或公网暴露。登录用本地测试身份/合成数据，凭据不放合同、日志或附件。此处定义前提，不要求本阶段启动服务或修改部署脚本。
